## Read closely before approving
- Scenario 25 (SH151, M85): the only proof of the "never miss a change" rule; it uses raw connections and is the likeliest to be flaky.
- Scenario 28 (M88): spec Outcome 9 says a lost-access record is "reported as a tombstone"; the Gate 1 decision made it a 403 with no body. Check this meets the spec.
- Scenarios 14 and 27 (MD2, M87): trigger tombstones at each location, including cascades and detach at only one location.
- Scenarios 20 and 40 (410 expired) build the old cursor with the `Encode` stub, so they fail now from setup (`NotImplementedException`), not from a 500; once `Encode` exists they assert the 410 and `changes.cursor_expired`.
- Scenarios 41 to 43 (T8): they read the real host, so they fail now only because Menu and Organization are not tracked yet (scenarios 42 and 43 first assert that something is tracked). The model check lists the module contexts by reflection over the host's `RestaurantManagement.*` assemblies; trigger names must contain `_stamp` and `_tombstone`.
- Scenario 29 forges the cursor age and back-dates the tombstone; it does not prove retention in real time.

## Assumptions
- Spec wording corrected (user decision 2A): lost access is a 403 on that location's feeds; the device drops its data; tombstones only for records leaving a location the member can still read.
- Names the tests fix, which the implementer must follow: Shared `ChangeCursor` (record: Feed, OrganizationId, LocationId, IssuedAt, LowerBound, NextBound, LastStamp, LastId), `ChangeCursorCodec(TimeProvider)` with `Encode` and `Decode(text, feed, organizationId, locationId)`, `ChangeFeeds` constants, `ChangesQuery.EffectivePageSize`, `ChangePageBuilder.Build(records, tombstones, after, pageSize)`, `ChangeTrackingSql.StampTrigger(prefix, table)`, `ApplyChangeTracking(database, tombstoneTable?)`. Their stubs exist and throw `NotImplementedException`.
- Message keys the tests fix in the Shared resource files: `ChangeCursorInvalid`, `ChangeCursorExpired`, `LocationRequired`. The page size message uses the implementer's own catalog key (the existing completeness test checks it exists in all three languages).
- Database names the tests read directly with SQL: column `change_stamp` on `menus`, `menu_categories`, `location_menus`, `locations`; table `menu_tombstones` with `entity_id`, `location_id`, `organization_id`, `deleted_at`. The `entity_type` value is not asserted.
- The edit-stamp test runs an update that changes no value (`SET updated_at = updated_at`), so the stamp trigger must fire on every update statement.
- (Review fix round) Scenario 44 now tests `ChangeReader` paging directly on PostgreSQL with fixed (ID, stamp) rows; the original note below stays true for the snapshot bound. `ChangeReader` has no other test of its own: it needs a real transaction snapshot, so it is proven through the menus feed (#25 and the paging and sync scenarios), as the plan says. No `ChangeReader` stub is created.
- The controller stubs (`MenuChangesController`, `LocationController.GetLocationChanges`) and the `GetLocationChangesAsync` stub throw directly, so the new endpoint tests fail with a 500 instead of a 404. `IMenuChangesService` and `MenuChangesService` are not created as stubs; the implementer adds them.
- The plan is Large (limit 40 scenarios); the user approved 43 so that T8 stays in this plan; scenarios that the spec lists separately (#1 and #2, #7 and #8 on the same feed) share a test where one setup proves both.
- Writes in endpoint tests go through the database context (not the HTTP write endpoints), so the tests do not depend on versions, idempotency keys or client-time headers.
- Test run note: in the one full affected run, 112 existing Web.Tests failed with PostgreSQL "too many clients already" (container limit of 500 connections, shared by every test database pool); the same classes passed when rerun alone (67 of 67). The 43 new Web tests each create a database, so they add to that load. If CI shows the same, lower the connection pool size in `TenantApiFactory` rather than touching these tests. The tester also used more than 6 runs of the new classes while checking failure reasons (7 plus the affected run).
- Infra note (user approved at implementation): test databases connect with `Pooling = false` to avoid "too many clients"; the three changes-feed classes that read twice run in a non-parallel `ChangesFeedCollection`. Scenarios 41 to 43 and the paging and sync scenarios depend on both.
