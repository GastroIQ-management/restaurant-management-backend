## T2 — Change stamps, tombstones and change reader
| Field | Value |
|---|---|
| Expected context | Shared already maps per-module tables through model builder extensions (`ApplyIdempotencyKeys(table)`, provider-aware `ApplyVersionTokens(Database)`). Module unit tests run on SQLite, so nothing PostgreSQL-only may reach a SQLite schema. Modules share one database, so database function and trigger names carry a module prefix |
| Expected result | `IChangeTracked` (a `ChangeStamp` 64-bit number, column `change_stamp`, written only by the database). `ChangeTombstone` (ID, organization ID, location ID or none, entity type, entity ID, change stamp, deleted at). `ApplyChangeTracking(Database, tombstoneTable?)` maps the stamp on every `IChangeTracked` entity (read back after insert and update, not a concurrency token, indexed by organization and stamp) and, when a table name is given, the tombstone table (indexed by organization, location, entity type, stamp). `ChangeTrackingSql` returns the SQL texts module migrations run: a stamp trigger (`change_stamp = pg_current_xact_id()` as bigint on insert and update) and a tombstone trigger body. `ChangeReader` reads the lower bound for the next cursor (`pg_snapshot_xmin(pg_current_snapshot())`) before it reads rows, pages (ID, stamp) rows of records and tombstones together ordered by (stamp, ID) from the cursor's position, keeps only the later entry when one ID is both changed and deleted, and returns the page, `hasMore` and the next cursor (the bound from the first page of a paging run is kept until the run ends) |
| Outcome | #5 and #10 mechanism (no write missed when commits finish out of order; tombstones never removed here); verified end to end in T4 |
| Files | add `src/RestaurantManagement.Shared/Data/Changes/IChangeTracked.cs`, `ChangeTombstone.cs`, `ChangeTrackingModelBuilderExtensions.cs`, `ChangeTrackingSql.cs`, `ChangeReader.cs`, `ChangePageBuilder.cs` (pure merge and paging) · change `docs/security/shared-matrix.md` · tests in `tests/RestaurantManagement.Shared.Tests/` |

- **Stubs created:** `Shared/Data/Changes/IChangeTracked.cs`, `ChangeTombstone.cs` (complete models), `ChangeTrackingModelBuilderExtensions.cs`, `ChangeTrackingSql.cs`, `ChangePageBuilder.cs` (records complete, `Build` throws). `ChangeReader` is not stubbed.

**Delivered:** `ChangePageBuilder.Build` (latest entry per ID, record wins on equal stamp; (stamp, ID) order with PostgreSQL uuid byte order). `ApplyChangeTracking` maps `change_stamp` (OnAddOrUpdate, no concurrency token, index on organization and stamp) and the tombstone table (snake_case columns); non-PostgreSQL providers get a constant default 0 so SQLite inserts work, PostgreSQL gets none. `ChangeTrackingSql.StampTrigger` and `TombstoneTrigger(prefix, table, tombstoneTable, entityType, locationExpression, organizationExpression = "OLD.organization_id")` (the last two let T3 handle tables without an `organization_id` column). `ChangeReader.ReadAsync(context, ChangeFeedRead<TItem>, ct)` takes the module's already scoped record and tombstone queries projected to `ChangeRow(Id, Stamp)`, reads `pg_snapshot_xmin` first, keeps the run's bound in the cursor, and is registered by `AddChangeCursors()`. `ChangeRow` and `ChangeFeedRead` live in `ChangeReader.cs`. Note: tombstones are also returned inside the paging run of a first sync (no cursor). SH rows stay ❌ until the final test run. Review fix: a source cut at `pageSize + 1` now sets a limit (its last row read); the earliest limit of the two sources drops every later row from both before `ChangePageBuilder.Build`, so a later record for the same ID can no longer hide an unread tombstone (`hasMore` is true whenever a source was cut). Added `ChangePageBuilder.IsAfter`. New test `ChangeReaderPagingPostgresTests` (SH152, scenario 44, user approved the new file). Decision taken: the fix also stops counting same-stamp rows at or before the position as "more" (a side effect of using the cut flag; no role, tenancy, money or data-loss impact).
