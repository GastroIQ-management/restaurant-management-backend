## T4 — Location create takes the client's ID
| Field | Value |
|---|---|
| Expected context | `POST api/v1/locations`: `CreateLocationRequest` (in `LocationModels.cs`) has no `Id`; `LocationService.CreateLocationAsync` sets `Id = Guid.NewGuid()` (line 51); only the Owner creates. `LocationService.SaveAsync` turns every unique violation into `LocationCodeAlreadyUsed`, so a primary key clash would be misreported as a taken code. ## T5 — Organization create takes the client's ID
| Field | Value |
|---|---|
| Expected context | `POST api/v1/organizations/create`: any signed-in user, no organization in the token needed. `OrganizationService.CreateOrganizationAsync` checks the trial limit first, then sets `Id = Guid.NewGuid()` (line 86), saves organization and settings in a transaction and sets up the Owner access through `IOrganizationAccessSetup`. A failed save is rolled back and rethrown as a plain `Exception` (500). The user's organizations are loaded and tracked (lines 65–69, allowed `IgnoreQueryFilters`), so adding a new one with one of their IDs fails in EF Core before reaching the database. Existing tests that post this create get an `id` in step 3 |
| Expected result | `id` required (400 when missing, null, malformed or empty); organization stored under it and returned with it. An ID already used by any organization (the user's own or another user's) answers 409 `id.already_used`, never 500: no organization, settings or Owner access is created. The trial-limit refusal keeps its place before the clash. Outcome #5 does not apply: this create makes the organization the token will later name |
| Outcome | #1–#4, #6; verified by endpoint tests in `tests/RestaurantManagement.Web.Tests/Organization/` and the OpenAPI check |
