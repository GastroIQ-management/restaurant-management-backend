## T7 — Invitation create takes the client's ID
| Field | Value |
|---|---|
| Expected context | `POST api/v1/invitations`: `CreateInvitationRequest` (in `Models/Invitations/InvitationModels.cs`) has no `Id`; `InvitationService.CreateAsync` builds it in `NewInvitation` (`Id = Guid.NewGuid()`, line 170) after the member and delegation checks (Members Manage at each invited location). It loads and tracks the open invitation for the same email (lines 88–90) and marks it replaced: a retried create with the same ID finds its own first invitation, and adding the new one fails in EF Core before reaching the database. `SaveOpenInvitationAsync` maps only the open-invitation index. The accept link uses a separate token (`InvitationTokens`), never the ID. The email is sent only after the save. Existing tests that post this create (`InvitationWebSupport` and others) get an `id` in step 3 |
| Expected result | `id` required (400 when missing, null, malformed or empty); invitation stored under it and returned with it. An ID already used (same or another organization, including the open invitation it would replace) answers 409 `id.already_used`, never 500: nothing is replaced, stored, audited or emailed. Organization from the token only |
| Outcome | #1–#6; verified by endpoint tests in `tests/RestaurantManagement.Web.Tests/Identity/` and the OpenAPI check |
