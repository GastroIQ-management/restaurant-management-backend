## T6 — Identity sign-in and account refusals name their codes
| Field | Value |
|---|---|
| Expected context | `SessionService`, `RegistrationService`, `VerificationService`, `PasswordChangeService` and `UserLanguageService` throw code-less `BusinessException`s. Login collapses unknown email, wrong password, locked and unverified account into one generic 401; verify collapses unknown email, wrong code and a verification lock into one generic 401 (module `CLAUDE.md`); the email-already-registered pre-check and the unique-violation catch answer alike. Session refusals (`InvalidOrExpiredToken`), select-organization refusals (organization required 400, not a member 403) and password-change refusals (wrong current password, same as current) each have their own message. The bodiless `Unauthorized()` results in `AuthController` and `UsersController` already get `auth.unauthorized` from T3 |
| Expected result | Every refusal of these services answers Problem Details with a code: one code for every collapsed login failure (for example `auth.invalid_credentials`), one for every collapsed verify failure (for example `auth.invalid_code`), one for an ended or invalid session, one for an already registered email (pre-check and race), and one each for the select-organization and password-change refusals. Codes live in a catalog per feature subfolder, marked as a catalog (T1); a code always answers one status, so select-organization's 400 does not reuse the 403 `organization.required`. Statuses, messages and response timing unchanged |
| Outcome | #1, #2: each sign-in and account refusal answers its code; checked by unit tests on `BusinessException.Code` and endpoint tests on the body |
