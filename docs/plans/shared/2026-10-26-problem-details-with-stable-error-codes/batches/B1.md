## T1 — Shared Problem Details answer and code catalog
| Field | Value |
|---|---|
| Expected context | `BusinessException` carries only a message and a status. `ExceptionHandlingMiddleware` answers `application/json` `{ message }` for it and `{ message, detail }` for an unexpected error (Sentry only for the latter; the last-resort path must never throw; English fallback when no localizer). Validation 400s are already RFC 9457 (Request for Comments 9457) Problem Details. Messages come from `IStringLocalizer<SharedResource>`. No new package: Problem Details types ship with ASP.NET Core |
| Expected result | `BusinessException` also carries a code; a constructor with the code is added, and the code-less one stays until T9, answering the fallback code of its status. A Shared catalog holds the cross-module codes (`validation.failed`, `auth.unauthorized`, `auth.invalid_token`, `access.denied`, `organization.required`, `organization.not_found`, `location.not_found`, `rate_limit.exceeded`, `server.unexpected_error`, `request.in_progress`) and one fallback code per status the host can answer (400, 401, 403, 404, 405, 409, 415, 429, 500; the 409 one is a lasting conflict). It flags exactly `server.unexpected_error`, `rate_limit.exceeded` and `request.in_progress` as retry codes. A marker identifies catalogs, so modules add their own and T8 lists them all. Codes are `<subject>.<reason>`, lowercase snake_case, fixed English, never reused; a code always answers one status; the tester fixes the exact names in `scenarios.md`. New message keys (English, Portuguese, French) give the fallback titles the host needs in T3 |
| Outcome | #1, #2, #3, #4: a refusal answers Problem Details with its code; the same refusal in `en`, `pt` and `fr` has one code and three titles; every code has the format and is unique; `request.in_progress` is the only retry code with status 409; the retry set is exactly the three codes; production 500 has no `detail` |
