## T2 — Menu edit and delete check the version
| Field | Value |
|---|---|
| Expected context | `PUT api/v1/menus/{menuId}` (`MenuService.EditMenuAsync`, line 106) loads and saves with no version check; `DELETE api/v1/menus/{menuId}` hard-deletes. Order today: 404 `menu.not_found` (tenant filter hides other organizations' menus), then Menus Manage at every linked location (`RequireManageMenuAsync`). `MenuResponse` has no version; it is built in three places (`GetMenusAsync`, `GetMenusByLocationAsync`, `GetMenuResponseAsync`). Menu-location link and unlink endpoints stay as they are |
| Expected result | `Menu` is versioned (T1 mapping in `MenuDbContext`). Every `MenuResponse` (create, edit, list, by location) carries `version`. Edit requires `version` in the body; delete requires `?version=`; missing answers 400 on the field, translated. After 404 and 403, a stale version answers 409 `version.conflict` with the current menu (`MenuResponse`) under `current` and changes nothing; the current version edits and returns the new `version`, or deletes. A race lost between read and save answers the same 409 |
| Outcome | #1–#6; verified by endpoint tests in `tests/RestaurantManagement.Web.Tests/Menu/` (PostgreSQL) and an OpenAPI check of `/swagger/v1/swagger.json` in `tests/RestaurantManagement.Web.Tests/Web/` |
| Files | `change` `src/RestaurantManagement.Modules.Menu/Entities/Menu.cs` · `change` `Data/MenuDbContext.cs` · `change` `Models/MenuResponse.cs`, `Models/EditMenuRequest.cs` · `change` `Services/MenuService.cs` · `change` `Controllers/MenuController.cs` (delete takes `version`) · `add` migration in `Migrations/` (ef-migration skill; it must add no `xmin` column) · `change` `docs/security/menu-matrix.md`, `docs/security/web-matrix.md` |
| Modules | Menu |
| Flags | Security: 409 body carries the menu, only after the access check |
| DoD | Tests written and passing · missing version 400 on edit and delete · stale edit 409 with `current` equal to the stored menu, menu unchanged · stale delete 409, menu and its categories still stored · current version edits and the response `version` differs from the one sent; a second edit with the old version answers 409 · cross-tenant: another organization's menu with its real version answers 404 `menu.not_found`, never 409, nothing about it in the body · a member with Menus Read only sending a stale version gets 403, not 409 · GET lists carry `version` · OpenAPI shows `version` on `MenuResponse`, `EditMenuRequest` and the delete parameter · `docs/security/menu-matrix.md` and `docs/security/web-matrix.md` rows added or changed and ✅ with their tests; `python3 .claude/scripts/check-security-matrices.py` passes |

**Delivered:** `Menu` is versioned (`IVersionedEntity`, `ApplyVersionTokens` in `MenuDbContext`). Every `MenuResponse` carries `version` (one `MapToResponse`). `EditMenuRequest.Version` and the delete `?version=` are `uint?` with `[Required]`, so a missing value answers 400 on the field; the service reads `request.Version ?? 0` because the unit tests build requests without a version. Edit and delete call `VersionCheck.Require` after the 404 and 403 checks and save through `VersionCheck.SaveAsync`; a lost race re-reads the stored menu (404 if gone). Migration `VersionMenus`: the generated `Up` added an `xmin` column, which PostgreSQL refuses, so `Up` and `Down` were emptied by hand (the plan requires no column); the snapshot is the generated one. Matrix rows M59-M66 are checked off; the web-matrix OpenAPI row stays until T6.
