## T4 — Location edit and delete check the version
| Field | Value |
|---|---|
| Expected context | `PUT api/v1/locations/{locationId}` (`LocationService.EditLocationAsync`, line 79) loads and saves with no version check; `DELETE` is a soft delete (Status set to Closed, an update). Order today: 404 `location.not_found` (tenant filter), then Locations Manage at the location, or the Owner when the edit closes it or on delete; then the taken-code check (409 `location.code_already_used`) and `SaveAsync`. A status change writes an audit entry after the save. `LocationResponse` comes from `MapToResponse` |
| Expected result | `Location` is versioned (T1 mapping in `OrganizationDbContext`). Every `LocationResponse` (create, list, edit) carries `version`. Edit requires `version` in `EditLocationRequest`; delete requires `?version=`; missing answers 400, translated. After 404 and 403, and before the taken-code check, a stale version answers 409 `version.conflict` with the current location under `current`, changes nothing and writes no audit entry; the current version edits and returns the new `version`, or closes the location |
| Outcome | #1–#6; verified by endpoint tests in `tests/RestaurantManagement.Web.Tests/Organization/` (PostgreSQL) and the OpenAPI check in `tests/RestaurantManagement.Web.Tests/Web/` |
| Files | `change` `src/RestaurantManagement.Modules.Organization/Entities/Location.cs` · `change` `Data/OrganizationDbContext.cs` · `change` `Models/LocationModels.cs` · `change` `Services/LocationService.cs` · `change` `Controllers/LocationController.cs` (delete takes `version`) · `add` migration in `Migrations/` (ef-migration skill; no `xmin` column added) · `change` `docs/security/organization-matrix.md`, `docs/security/web-matrix.md` |
| Modules | Organization |
| Flags | Security: 409 body carries the location, only after the access check |
| DoD | Tests written and passing · missing version 400 on edit and delete · stale edit and stale delete 409 with `current`, location unchanged (still open), no audit entry · stale version with a taken code answers `version.conflict`, not the code error · current version succeeds and returns a new `version` · cross-tenant: another organization's location with its real version answers 404 `location.not_found`, never 409 · a member with Locations Read only sending a stale edit, and a non-Owner sending a stale delete, get 403, not 409 · OpenAPI shows `version` on `LocationResponse`, `EditLocationRequest` and the delete parameter · `docs/security/organization-matrix.md` and `docs/security/web-matrix.md` rows added or changed and ✅ with their tests; `python3 .claude/scripts/check-security-matrices.py` passes |
| Depends on | T1 |
| Uses from dependency | Versioned entity mapping, version check, `ErrorCodes.VersionConflict`, version conflict exception |

## T5 — Organization edit checks the version

|---|---|
| Expected context | `PUT api/v1/organizations/edit` (`OrganizationService.EditOrganizationAsync`, line 197): the organization comes from the token; 404 when missing, then the Owner check; it saves the organization row and its settings row in one save (always touching the organization's `UpdatedAt`) and records a settings audit entry after. `OrganizationResponse` (create, list, edit) comes from `ToResponse`. `Organization` is a `BaseEntity`, not a tenant entity; the list reads with `IgnoreQueryFilters` (allowed place, unchanged) |
