# B3 — Choosing an organization keeps the login time

**Module:** Identity   **Depends on:** T2 (B2)   **Tasks:** T3

## T3 — Choosing an organization keeps the login time

**Outcome:** #3, #5   **Priority:** P1

### Context
- After T2, rotation copies `SessionStartedAt`, so switching with the caller's own cookie already keeps the login time.
- The gap is the fallback in `SelectOrganizationAsync`. With no usable cookie it calls `IssueAsync`, which starts a new session family and restarts the 30 days. A stolen cookie could reach that path (refresh, then switch without the cookie) and outlive the absolute limit.
- `SelectOrganizationAsync` keeps the user and membership checks (S3 403, S4 401) in their current order.
- It then rotates only the caller's own cookie.
- It returns 401 `InvalidOrExpiredToken` and issues no token in these cases:
  - no cookie
  - an unknown, expired, idle or past-30-day cookie
  - another user's cookie
- The `IssueAsync` fallback is removed.
- The other option, if the architect prefers it at Gate 1, keeps today's new session (S6, S8):
  - The access token carries the login time as an `auth_time` claim, and the new family reuses it.
  - That changes `AccessTokenFactory`, `ISessionService`, `AuthController` and the token contract.
